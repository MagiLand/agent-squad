### Startup method and timing

The probe imports the unchanged installed `ReviewWorktree`, `open_reviewer`,
`start_reviewer`, and `close_reviewer`. Each run creates a fresh detached
worktree at the pinned trial head, opens it with `herdr worktree open --cwd
<trial-primary> --path <worktree> --label <name> --no-focus`, and starts the
specified harness in the returned root pane. It uses the same ownership and
cleanup checks as the installed Reviewer lifecycle.

`base` uses the actual configured `reviewer.start_args=[]`. `args` uses
`('--verbose',)` for Claude and `('--no-alt-screen',)` for Codex, supplied to
the runtime configuration in memory and passed after Herdr's `--`. These are
diagnostic argument variants, not claims about the old failed runs. No model,
approval, trust, sandbox, or persisted configuration setting was changed.
The Codex startup matrix does not supply an initial review prompt.

Observation begins immediately before `start_reviewer` in a worker thread;
the observer calls `herdr agent get <name>` on a one-second schedule while the
start command is pending. A 45-second observation cap was never reached.
Every run first encountered a pre-launch `agent_pane_busy` refusal as the shell
initialized; the existing bounded shell retry handled it. Codex `args-3` had
two such refusals; all other runs had one. These refusals start no agent and
are distinct from `agent_not_ready`.

All times are on 2026-09-25 UTC. Transition entries are seconds after the
run's start timestamp: `N` = agent not yet found, `U` = `unknown`, `W` =
`working`, `I` = `idle`. They record every **observed** transition, not
sub-second transitions between samples. First-idle time includes the existing
shell retry; start duration measures only the final successful Herdr CLI call.
Milliseconds describe recorded sample times, not sub-second readiness accuracy.
All 20 start calls returned success with interactive readiness confirmed.

### Delivery findings

Installed `REVIEW_DELIVERY` selects `agent_prompt` for Claude and
`initial_prompt` for Codex. For Claude, `launch` waits for `start_reviewer`
to return, validates the returned agent object, calls `client.prompt`, then
performs a fresh `inspect_agent` read. The first validation is of the startup
response, not an independent immediate read before Herdr's readiness wait.
The exception handler retains resources for `agent_not_ready` from either
startup or prompt delivery, but the full adapter error names the failed command.
The historical outputs therefore locate the operation, as detailed below.

The separate Claude probe in `w14:p1` recorded:

The early prompt was rejected rather than queued. Herdr's

has the same guard. No keys were sent, and no permission/trust dialog was answered.

### Original error provenance

The issue #46 record describes both failures as a blocked startup signal.
The original Implementer tool outputs, checked directly during this revision,
contain the following error for `reviewer-pr7-d48ba66` and
`reviewer-pr66-f5a6685`, respectively:

```text
herdr agent start failed (agent_not_ready): agent <reviewer-name> is blocked during startup and is not ready for prompts
```

Installed `HerdrClient._run` constructs its prefix from the first two Herdr
arguments, so `agent start` and `agent prompt` failures are distinguishable.
The remaining message identifies the readiness loop's `blocked` branch in
[Herdr v0.9.0](https://github.com/herdrdev/herdr/blob/v0.9.0/src/cli/agent.rs#L607-L611).
The complete CLI source file is byte-identical in v0.9.1. Thus neither original
failure reached the post-start validation or delivery stages. Timeout,
post-start single-read timing, and early/post-start prompt delivery are excluded
for these two incidents, rather than left as possibilities merely because
other operations can return the same error code.

Herdr's [v0.9.1 CLI readiness loop](https://github.com/herdrdev/herdr/blob/v0.9.1/src/cli/agent.rs#L562)
and [v0.9.0 loop](https://github.com/herdrdev/herdr/blob/v0.9.0/src/cli/agent.rs#L562)
poll every 100 ms. `working`/`unknown` keep waiting; readiness requires
`idle`/`done` with `interactive_ready=true`. A detected `blocked` state returns
`agent_not_ready` immediately. Expiration returns `timeout`, a different error.
The [startup configuration](https://github.com/herdrdev/herdr/blob/v0.9.1/src/app/agents.rs#L8)
defaults to 30 seconds, with a three-second settling interval; accepted explicit
timeouts are greater than 3,000 and no more than 300,000 ms. Installed CLI help
and schema agree. None of the measurements overrode the timeout.

| Candidate cause | Observation and disposition |
| --- | --- |
| Claude simply exceeds a 30-second wait | Ruled out for the original incidents: their full error identifies startup blocking, not timeout. Both Herdr versions return `timeout` on expiry. A slow launch producing a transient blocked signal is a different, still unproven explanation. |
| Agent Squad's post-start single read | Ruled out for the original incidents: `agent start` failed before that validation/read was reached. The helper normally waits for interactive readiness first. |
| First Claude launch in a never-trusted fresh clone | Reproduced: a real trust dialog caused the same startup-blocked error; it remained blocked without input and trust keys stayed absent. This is the leading explanation for the original fresh-clone incidents, not proof of their unseen screens or intervening human actions. Task B's documented trust prompt and Task A's later successful launch support it; the original panes' later idle state leaves the intervening transition unresolved. |
| Every linked worktree needs its own trust entry | Not required in the tested layout: all 26 launches under the already-trusted primary reached readiness without separate worktree entries. This observation does not cover first launch under an untrusted primary. |
| `reviewer.start_args` alone causes failure | Neither empty arguments nor the two explicit diagnostic variants produced a startup failure. Other argument combinations and the historical configuration remain outside this sample. |
| Early or post-start prompt-delivery race | Ruled out for the original incidents: their full error names `agent start`. The deliberately reordered prompt probe exercises a different operation; normal delivery was never reached in those failures. |
| Why the original startup `blocked` signal later became `idle` | Unresolved. First-launch trust is now the leading candidate, but the original failure-time terminal snapshots and any intervening human actions are unestablished. A transient false detection is not reproduced. A later idle pane alone cannot distinguish these possibilities. |

The doctor skill mismatch is a separate environment limitation, not an
explanation for the historical Reviewer startup failures. Correcting it would
change an explicitly frozen baseline and was not attempted.

## Scope and limitations

The startup matrix ran from 13:39 to 13:43 UTC, the initial delivery probe
finished at 13:46:10 UTC, and the additional fresh-trust experiment finished
at 14:23:28 UTC on 2026-09-25. This bounded investigation took less than one
working day. It completed the matrix, CLI attempts, supplemental probes,
delivery and fresh-trust checks, original-error verification, source comparison,
and cleanup; it did not become a runtime repair.

The already-trusted matrix is a current-machine negative result, while the
fresh-clone trust experiment is a positive reproduction of startup blocking.
Neither proves the original screen contents or subsequent transition to idle.
Harness versions changed since the release trials; neither original failed
pane was preserved for startup-time inspection, although both full error
messages survive and were checked.
One-second sampling can miss shorter states, and five samples per group
cannot establish a reliable tail bound. Runs were sequential in fresh
workspaces, not a load/stress test. The configured primary trust and normal
user integrations were retained. No permission bypass, synthetic blocked-state
injection, historical-version downgrade, or global configuration edit was used.

The matrix and fresh-clone experiment exercised installed startup helpers
against real harnesses; neither launched a real review request or ran
`reviewer adopt`. Doctor CLI
was attempted five times but never reached its live stage. Direct function
calls supplement that missing observation without claiming equivalent CLI
validation. The forced early prompt reproduced an error code on another
operation and is not used to explain the original failures. The fresh-clone
experiment reproduced their startup-blocked signal with a visible cause; it
never reached idle during observation, and trust was not granted.

## Recommendation for Increment 4

**Do not add the proposed post-error wait on this evidence.** Plan §6 proposes
a bounded wait **after `agent_not_ready`**, followed by a state read that delivers
only to an `idle` agent and leaves a `blocked` agent subject to §8.4. This is
different from extending Herdr's existing readiness timeout.

The proposal could help if startup falsely or transiently reported `blocked`
and then became idle without human action. That transition has not been
reproduced or timed. In the fresh-clone reproduction, the real trust question
persisted across 15 seconds of post-error observation; a re-read would still
find `blocked`. The later idle inspection of the historical panes establishes
neither an automatic transition nor a safe wait duration. The trusted-primary
timing distribution also cannot size a wait after a blocked-startup error.
No new wait bound or polling interval is therefore justified.

Keep §8.4's retained-resources behavior and normal Developer trust resolution
followed by adoption. First-launch trust preparation for fresh checkouts is the
concrete operational concern demonstrated here; this experiment did not reveal
a defect in that gate. Treat the original blocked-to-idle transition as the
remaining historical uncertainty, rather than presuming a product defect or
reopening the already-excluded prompt-delivery and timeout explanations.

If an unexplained recurrence requires further investigation, preserve its
contemporaneous passive trust-dialog/detection snapshot and establish any human
actions before the later state. A demonstrated automatic blocked-to-idle
transition could justify a separate focused follow-up and measurements for the
plan's post-error re-read. No speculative fix or additional issue was created
here. The doctor installation mismatch also needs a separately authorized
baseline refresh before an end-to-end CLI live-probe rerun.
