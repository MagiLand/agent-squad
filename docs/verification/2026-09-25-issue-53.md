### Startup method and timing

The probe imports the unchanged installed `ReviewWorktree`, `open_reviewer`,
`start_reviewer`, and `close_reviewer`. Each run creates a fresh detached
worktree at the pinned trial head, opens it with `herdr worktree open --cwd
<trial-primary> --path <worktree> --label <name> --no-focus`, and starts the
specified harness in the returned root pane. It uses the same ownership and
cleanup checks as the installed Reviewer lifecycle.

`base` uses the actual configured `reviewer.start_args=[]`. `args` uses
`('--verbose',)` for Claude and `('--no-alt-screen',)` for Codex, supplied to
the runtime configuration in memory and passed after Herdr's `--`. These are
diagnostic argument variants, not claims about the old failed runs. No model,
approval, trust, sandbox, or persisted configuration setting was changed.
The Codex startup matrix does not supply an initial review prompt.

Observation begins immediately before `start_reviewer` in a worker thread;
the observer calls `herdr agent get <name>` on a one-second schedule while the
start command is pending. A 45-second observation cap was never reached.
Every run first encountered a pre-launch `agent_pane_busy` refusal as the shell
initialized; the existing bounded shell retry handled it. Codex `args-3` had
two such refusals; all other runs had one. These refusals start no agent and
are distinct from `agent_not_ready`.

All times are on 2026-09-25 UTC. Transition entries are seconds after the
run's start timestamp: `N` = agent not yet found, `U` = `unknown`, `W` =
`working`, `I` = `idle`. They record every **observed** transition, not
sub-second transitions between samples. First-idle time includes the existing
shell retry; start duration measures only the final successful Herdr CLI call.
Milliseconds describe recorded sample times, not sub-second readiness accuracy.
All 20 start calls returned success with interactive readiness confirmed.

### Delivery findings

Installed `REVIEW_DELIVERY` selects `agent_prompt` for Claude and
`initial_prompt` for Codex. For Claude, `launch` waits for `start_reviewer`
to return, validates the returned agent object, calls `client.prompt`, then
performs a fresh `inspect_agent` read. The first validation is of the startup
response, not an independent immediate read before Herdr's readiness wait.
The exception handler retains resources for `agent_not_ready` from either
startup or prompt delivery, so the error code alone cannot locate the operation.

has the same guard. No keys were sent, and no permission/trust dialog was answered.

## Defects found and fixed

No product defect was fixed. The investigation distinguishes the candidate
mechanisms instead of attributing every `agent_not_ready` to slow startup.

Herdr's [v0.9.1 CLI readiness loop](https://github.com/herdrdev/herdr/blob/v0.9.1/src/cli/agent.rs#L562)
and [v0.9.0 loop](https://github.com/herdrdev/herdr/blob/v0.9.0/src/cli/agent.rs#L562)
poll every 100 ms. `working`/`unknown` keep waiting; readiness requires
`idle`/`done` with `interactive_ready=true`. A detected `blocked` state returns
`agent_not_ready` immediately. Expiration returns `timeout`, a different error.
The [startup configuration](https://github.com/herdrdev/herdr/blob/v0.9.1/src/app/agents.rs#L8)
defaults to 30 seconds, with a three-second settling interval; accepted explicit
timeouts are greater than 3,000 and no more than 300,000 ms. Installed CLI help
and schema agree. None of the measurements overrode the timeout.

| Candidate cause | Observation and disposition |
| --- | --- |
| Claude simply exceeds a 30-second wait | Ruled out as the direct mechanism producing the recorded startup error code: both relevant Herdr releases return `timeout` on expiry. The matrix's maximum first-idle time was 16.015 s. A slow launch that also produces a transient blocked signal remains a separate possibility. |
| Agent Squad's single read precedes readiness | Ruled out for the normal code path: `start_reviewer` synchronously waits for Herdr, and the first validation checks the completed startup response. A state change after that response is not excluded. |
| Missing linked-worktree trust | Not observed under current versions: primary trust exists, no linked-worktree entries were needed, and all 26 real launches reached readiness. This does not reconstruct trust at the two original failures. |
| `reviewer.start_args` alone causes failure | Neither empty arguments nor the two explicit diagnostic variants produced a startup failure. Other argument combinations and the historical configuration remain outside this sample. |
| Claude's normal prompt is sent while startup is pending | The forced early submission was rejected, not queued, but normal `launch` orders it after readiness. The intentionally reordered probe is not a reproduction of the original launch path. |
| Transient genuine dialog or false `blocked` detection | Unresolved. No such transition appeared in the current runs; the original failure-time terminal snapshots are absent. A later idle pane cannot distinguish a transient dialog from detection error. |

The doctor skill mismatch is a separate environment limitation, not an
explanation for the historical Reviewer startup failures. Correcting it would
change an explicitly frozen baseline and was not attempted.

## Scope and limitations

The live startup matrix ran from 13:39 to 13:43 UTC; all diagnostic live work
finished by 13:46 UTC on 2026-09-25. This bounded investigation took less than
one working day. It stopped after completing the matrix, CLI attempts,
supplemental probes, delivery check, source comparison, and cleanup; it did
not become a runtime repair.

This is a current-machine negative result, not proof that the original
incidents cannot recur. Harness versions changed since the release trials;
neither original failed pane was preserved for startup-time inspection.
One-second sampling can miss shorter states, and five samples per group
cannot establish a reliable tail bound. Runs were sequential in fresh
workspaces, not a load/stress test. The configured primary trust and normal
user integrations were retained. No permission bypass, synthetic blocked-state
injection, historical-version downgrade, or global configuration edit was used.

The matrix exercised the installed startup helpers against real harnesses;
it did not launch a real review request or run `reviewer adopt`. Doctor CLI
was attempted five times but never reached its live stage. Direct function
calls supplement that missing observation without claiming equivalent CLI
validation. The forced early prompt reproduced an error code on another
operation, not the original failure mechanism.

## Recommendation for Increment 4

**Do not add the proposed bounded wait on this evidence.** Keep the §8.4
retained-resources behavior and require normal Developer resolution/adoption
when a real blocked prompt occurs. The existing 30-second wait covered every
measured startup, and timeout is not the recorded error mechanism. There is
no reproduced slow-start cause from which to justify a new wait bound,
polling interval, or terminating read.

The historical startup defect remains a follow-up investigation, rather than
an Increment 4 wait implementation. On recurrence, capture the failing
operation, complete error body, contemporaneous agent state and passive
terminal snapshot, then later state without sending input. That evidence can
separate a genuine transient dialog, false blocked detection, and a post-start
delivery race. This record does not create another issue merely to track a
speculative fix; no runtime change is recommended until that distinction is
established. The doctor installation mismatch also needs a separately
authorized baseline refresh before an end-to-end CLI live-probe rerun.
